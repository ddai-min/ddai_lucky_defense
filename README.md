# 운빨 디펜스 (Lucky Defense)

스타크래프트 유즈맵 「메이플 운빨 디펜스」 계열의 **뽑기 기반 랜덤 디펜스** 게임입니다.
Flutter + [Flame](https://flame-engine.org) 게임 엔진으로 만들었고, **이미지 에셋이 전혀 없이**
전부 Canvas 드로잉과 이모지로 렌더링합니다.

**웹에서 바로 플레이** → <https://ddai-min.github.io/ddai_lucky_defense/>

## 실행

```bash
fvm flutter pub get
fvm flutter run            # 또는 ./.fvm/flutter_sdk/bin/flutter run
fvm flutter test           # 게임 로직 + 반응형 레이아웃 테스트
```

세로 화면 기준으로 설계했지만 레이아웃은 화면 크기에 맞춰 계산되므로
폰·태블릿·데스크톱 어디서든 동작합니다.

## 게임 규칙

| 요소 | 내용 |
| --- | --- |
| 소환 | 골드를 내면 **무작위 등급**의 유닛이 빈 슬롯에 배치됩니다. 보유 유닛이 많을수록 소환 비용이 올라갑니다. |
| 슬롯 | 한 줄 7칸 × 3줄 = **21칸 고정**. 화면이 커지면 칸 수가 아니라 칸 크기가 커집니다. |
| 자동 판매 | 자리가 없을 때 소환을 누르면 **가장 낮은 등급**이 자동으로 팔리고 그 자리에 들어옵니다. 3개 맞춰 둔 합성 세트는 건드리지 않습니다. 조작 패널에서 끌 수 있습니다(기본 켜짐). |
| 합성 | **같은 유닛 3개** → 상위 등급 유닛 1개. 슬롯도 2칸 비고 전투력은 올라갑니다. |
| 등급 | 노말 → 레어 → 유니크 → 에픽 → 레전더리 → **신화** → **초월** (신화 이상은 합성 전용) |
| 모드 | 인트로에서 **쉬움 · 보통 · 어려움 · 무한** 중에서 고릅니다. 앞의 셋은 100 웨이브를 막아내면 승리하고, 무한은 끝이 없습니다. |
| 도박 | **어려움에서만** 신화 3개를 초월로 올리는 합성이 15% 확률입니다. 실패하면 2기가 사라지고, 성공하면 공격력이 4배인 초월이 나옵니다. 자동 합성은 도박을 걸지 않습니다. |
| 웨이브 | 22초마다 자동 시작. 몬스터는 🌀에서 나와 지그재그 경로를 한 바퀴 돌아 🏰에 닿으면 라이프가 깎입니다. |
| 보스 | 10웨이브마다 등장. 처치하면 다이아를 줍니다. 뚫리면 라이프 5 소모. |
| 러시 | 5·15·25… 웨이브는 체력이 낮은 대신 수가 많고 빠릅니다. |
| 강화 | 골드로 공격력/공격속도/골드획득, 다이아로 **행운**(상위 등급 확률)과 라이프를 올립니다. |
| 고급소환 | 다이아 8개. **합성까지 하나 남은 유닛이 있으면 그 유닛을 콕 집어 줍니다**(유니크~레전더리). 없으면 유니크 이상 무작위. 무엇이 나올지 버튼에 미리 뜹니다. |
| 최고 기록 | 도달 웨이브 기준으로 기기에 저장됩니다. HUD의 🏆, 인트로, 결과 화면에 표시됩니다. |

**조작** — 유닛 탭: 정보·판매·합성 / 유닛 드래그: 자리 교체 / 빈 곳 탭: 선택 해제 /
우측 하단 ⏸: 일시정지(멈춘 동안에는 조작 패널도 잠깁니다)

### 유닛 공격 타입

`단일` `광역` `둔화` `중독` `연쇄` `처형`(즉사 확률) `약탈`(골드 추가 획득)

등급이 오를수록 **사거리도 넓어져** 신화 이상은 두 칸 건너 레인까지 닿습니다.
사거리는 화면 픽셀이 아니라 레인 간격(밴드)의 배수로 정의되어 해상도와 무관하게 같은 체감을 줍니다.

## 밸런스 조정

수치는 전부 [`lib/game/data/balance.dart`](lib/game/data/balance.dart) 한 곳에 모여 있습니다.

```dart
static const List<double> damage = [10, 34, 116, 400, 1400, 5200, 21000]; // 등급별 공격력
static const double baseHp = 110;                                          // 1웨이브 체력(전 모드 공통)
static double enemyHp(int wave, GameMode mode) { ... }                     // 몬스터 체력 곡선
static int summonCost(int unitCount) => 24 + 8 * unitCount;               // 소환 비용
static List<double> summonWeights(int luck) { ... }                       // 등급별 소환 확률
```

유닛을 추가하려면 `unit_catalog.dart`의 `kUnitCatalog`에 `UnitSpec` 한 줄만 넣으면
도감·소환·합성에 자동으로 반영됩니다.

### 난이도 시뮬레이터

수치를 바꿨을 때 실제로 몇 웨이브까지 버티는지 감이 아니라 숫자로 봅니다.
공식은 `Balance` 를 그대로 가져다 쓰므로 게임과 어긋나지 않습니다.

```sh
dart run tool/balance_sim.dart           # 현재 밸런스 리포트
dart run tool/balance_sim.dart --curve   # 웨이브별 여유 (--easy / --normal / --hard 로 모드 지정)
dart run tool/balance_sim.dart --levers  # 조정 레버별 효과 비교
dart run tool/balance_sim.dart --luck    # 운이 당락을 가르는지 측정
dart run tool/balance_sim.dart --gems    # 다이아를 어디에 쓰는 게 이득인지
```

**쉬움·보통·무한의 난이도는 몬스터 체력 곡선 하나로만 갈립니다.**
어려움만 규칙이 하나 더 다릅니다(아래 «어려움은 왜 규칙이 다른가»).

모든 곡선은 `baseHp`(1웨이브 체력)에서 출발합니다. 이 한 값이 전 모드의 체력을
곱으로 밀어 올리는 손잡이입니다.

| 모드 | 곡선 | 30웨 | 60웨 | 100웨 | 100웨 도달률 |
| --- | --- | --- | --- | --- | --- |
| 쉬움 | `110 × 1.10^(w-1)` | 1,745 | 30,448 | 1,378,061 | 98% |
| 보통 | 꺾인 곡선(아래) | 7,127 | 140,116 | 1,828,596 | **13%** |
| 어려움 | 꺾인 곡선 + 초월 도박 | 8,933 | 206,318 | 3,094,163 | **3%** |
| 무한 | `110 × 1.17^(w-1)` | 10,442 | 1,159,734 | 619,145,895 | — |

보통은 단순히 배율을 올린 게 아니라 **곡선 모양이 다릅니다.** 플레이어 전투력은
«초월» 에서 멈추므로 후반에는 더 늘지 않습니다. 체력만 끝까지 같은 비율로 올리면
중반 50 웨이브가 손 놓아도 되는 구간이 되고 마지막 몇 웨이브만 난이도가 됩니다 —
쉬움 곡선이 딱 그렇습니다(중반 여유가 10배 안팎까지 벌어집니다). 그래서 보통은
증가율을 웨이브마다 조금씩 꺾어(`1.186`에서 시작해 매 웨이브 `0.9875`배) 여유가
처음부터 끝까지 비슷하게 유지되도록 했습니다.

못 깨는 판도 88 웨이브까지는 갑니다. **«중반에 무너졌다» 가 아니라 «결승선
앞에서 놓쳤다» 로 끝나도록** 맞춘 것입니다. 여기서 증가율을 0.002만 더 올리면
숙련자 도달률이 5분의 1 이하로 주저앉습니다(`1.186`→`1.188` 에서 85%→18%) —
후반에는 플레이어가 한계에 닿아 더 셀 수 없기 때문에 이 언저리가 난이도가 급격히
꺾이는 지점입니다.

**도달률은 실력 분포 전체에 걸쳐 잽니다.** 커버리지를 한 값으로 고정해 재면
도달률이 100% 아니면 0%로 튑니다 — 후반에는 누구나 «초월» 에서 멈춰 전투력이
같아지기 때문에, 그 한 사람이 깨느냐 마느냐로 결과가 갈리는 탓입니다.

**모델에서 가장 불확실한 값은 «커버리지»** 입니다. 사거리 밖이거나 재장전 중이라
명목 DPS 가 전부 몬스터에게 닿지는 않는데, 이걸 숙련자 0.80 · 라이트 0.55 로 가정합니다.
유닛 배치 전략과 둔화·중독 시너지는 모델에 없습니다. **절대 웨이브 수는 어림값이고,
레버 사이의 상대 비교가 믿을 만한 부분**입니다.

모델은 등급별 기본치만 쓰고 **유닛마다 붙은 배율(`UnitSpec.dmg`·`spd`)은 무시합니다.**
초월 셋은 배율 곱이 1.92라 등급 기본치보다 그만큼 세고, 그래서 실제 게임에서는
초월 한 기의 값어치가 모델보다 큽니다(실측 DPS 25.0만 대 신화 9.3천 = 26.8배, 모델은
18.1배). 어려움 도달률 3% 는 그만큼 보수적으로 잡힌 값입니다.

초월 셋(창세의신 🌟 광역 · 종말의신 ☄️ 처형 · 심판의신 ⚖️ 단일)은 **DPS 가 서로 같습니다.**
갈리는 건 공격 방식과 사거리뿐이라 합성에서 무엇이 나오든 기본 전투력은 그대로입니다
(도박의 기댓값 계산이 등급 기본치로 서 있기 때문입니다). 테스트가 이 조건을 지킵니다.
다만 종말의신의 즉사는 DPS 밖의 덤이라 모델에 잡히지 않습니다 — 많이 뽑으면 실제로는
그만큼 더 셉니다. 그것도 운입니다.

### 고급소환은 왜 «콕 집어» 주는가

다이아 수입은 한 판에 95개(보스 10번)인데 **행운을 끝까지 올리는 데만 225개**가 듭니다.
한 판에 행운을 채울 수 없으니, 다이아는 언제나 행운에 넣는 게 이득입니다 — 12다이아짜리
고급소환은 행운 3~4레벨을 포기하는 값이었습니다. 게다가 보장하는 건 **등급뿐이고 종류는
복불복**이라, 유니크 4종 중 필요한 게 나올 확률은 1/4 입니다. 비싼 값을 치르고도 쓸모없는
유닛이 나오는 구조였습니다.

`--gems` 가 정책을 겨뤄 줍니다.

```
다이아 쓰는 법            무한    보통    어려움
전부 행운                 43웨    79%      6%
전부 고급소환             42웨     0%      0%
행운 6렙까지 → 고급소환   43웨     0%      3%
행운 10렙까지 → 고급소환  43웨    21%      4%
행운 14렙까지 → 고급소환  43웨    81%      6%
```

**전부 고급소환은 파국이고, 섞어 써도 그냥 행운만 올린 것과 같습니다.** 가격을 내리거나
효과를 키운 안도 전부 오차 범위(±3%p) 안이었습니다. 즉 이건 **성능 문제가 아니라 체감
문제**이고, 그래서 밸런스 위험 없이 «누를 맛» 만 고칠 수 있었습니다.

- 종류까지 보장합니다 — 2개 모아 둔 유닛이 있으면 **그걸** 줍니다. 복불복이 사라집니다.
- 무엇이 나올지 누르기 전에 보여 줍니다(자동 판매 예고와 같은 방식).
- 8다이아로 내렸습니다 — 40웨이브 이후 **보스 하나가 고급소환 한 번**이 되는 리듬입니다.

신화 이상은 겨냥하지 않습니다. 합성 전용 등급을 돈 주고 사면 등급 규칙이 깨집니다.

근본 원인(행운이 다이아를 독식하는 구조)은 그대로입니다. 이걸 바꾸려면 행운 비용 곡선을
손봐야 하는데, 그건 모든 모드의 밸런스를 다시 맞추는 일이라 따로 두었습니다.

### 어려움은 왜 규칙이 다른가

이름은 «운빨» 디펜스인데, **운은 사실상 아무것도 결정하지 않습니다.** 실력을
고정하고 400판을 돌리면 100웨이브에서 판마다 벌어지는 전투력 차이가 1.10배뿐이고,
끝난 웨이브도 전부 99~100입니다. 한 판에 유닛을 수백 번 뽑으니 뽑기 운은 평균으로
수렴하고, 후반에는 누구나 21칸을 초월로 채워 같은 자리에서 멈추기 때문입니다.

그래서 **체력만 올리면 «운 좋으면 깬다» 가 아니라 «아무도 못 깬다» 가 됩니다.**
실력이 조금만 달라져도 도달률이 통째로 뒤집힙니다(보통: 0.70 에서 10%, 0.80 에서 90%).

어려움은 최고 등급을 도박으로 만들어 그 편차를 벌립니다. `--luck` 이 재는 값입니다.

```
운빨 폭 — 같은 실력, 판마다 벌어지는 전투력 (p90 ÷ p10)
모드     20웨    40웨    60웨    80웨    100웨
보통     2.47    1.64    1.35    1.18    1.10
어려움   2.47    1.62    7.65    3.35    2.38

실력별 100웨이브 도달률 — 평평할수록 운이 가른다
모드     0.55    0.65    0.70    0.75    0.80
보통     0%      0%       0%      8%     79%
어려움   0%      4%       4%      6%      6%
```

보통은 실력 0.75 와 0.80 사이에서 8%→79% 로 튀는 반면, 어려움은 실력을 통째로
바꿔도 3~6% 에 머뭅니다. **당락을 가르는 게 실력이 아니라 뽑기입니다.**

초월을 4배로 키운 건 연출이 아니라 **도박이 성립하기 위한 조건**입니다. 신화 3개를
그대로 두면 21,528 DPS 인데 15% 에 걸어 실패하면 1개만 남으므로, 초월이 원래 수치면
기댓값이 10,982 로 반토막입니다 — 즉 **합성하지 않는 쪽이 최적**이 되어 규칙이 통째로
함정이 됩니다. 4배로 키우면 기댓값이 25,630(1.19배)이 되어 거는 쪽이 이득이 됩니다.

이 보정을 모든 모드에 주면 쉬움·보통이 복구 불가능해집니다. 전투력 곡선이 계단이
되어 곡선이 그 계단 위나 아래에만 놓이기 때문입니다 — 쉬움은 증가율 1.12 에서 100%,
1.14 에서 0% 로 튀고 중간이 없습니다. 그래서 도박도 보정도 **어려움 전용**이고,
쉬움·보통·무한 수치는 한 줄도 건드리지 않았습니다.

어려움에서 못 깨는 판은 중반에 멈춥니다(라이트 기준 45웨이브). 보통과 달리 «결승선 앞»
이 아닙니다. 벽을 뒤로 밀 수는 있지만(`taper` 를 1.0 쪽으로) 그러면 30웨이브 여유가
3.1배에서 11.6배로 벌어져 **보통보다 쉬운 «어려움»** 이 됩니다. 60웨이브 운빨 폭이
8배라 한 곡선으로 «운 나쁜 판» 과 «운 좋은 판» 을 동시에 팽팽하게 만들 수는 없습니다.

시뮬레이터가 알아낸 것 중 직관과 어긋나는 것들:

| 조정 | 생존 웨이브 변화 |
| --- | --- |
| 슬롯 18 → 24 | **±0** — 슬롯이 늘면 소환 비용도 오르고, 어차피 합성으로 압축된다 |
| 강화 비용 대폭 인하 | **±0** — 효과는 선형, 체력은 지수라 못 따라간다 |
| 보스 체력 ×32 → ×20 | **±0** — 보스는 사망 원인이 아니다(창이 1.65배 길어 오히려 여유) |
| 라이프 20 → 30 | +2 — 무너지기 시작하면 순식간이라 버퍼가 무의미하다 |
| 몬스터 체력 증가율 | **압도적** — 사실상 이것 하나가 난이도를 결정한다 |
| 골드 수입 ×0.5 | 운빨 폭 **±0** — 뽑는 횟수를 줄여도 평균으로 수렴하는 건 똑같다 |
| 상위 합성을 도박으로 | 운빨 폭 1.10배 → **2.38배** — 편차를 벌리는 건 이것뿐이다 |
| 소환 비용 `20+6n`→`28+10n` | 체력은 그대로인데 보통 도달률 26% → **0%** — 체력 못지않게 센 레버다 |

## 웹 배포

GitHub Pages 에 올라간다. `main` 에 푸시하면
[`.github/workflows/web-deploy.yml`](.github/workflows/web-deploy.yml) 이
analyze · test 를 돌린 뒤 빌드해서 배포한다. 수동으로 돌리려면 Actions 탭의
«웹 배포» 에서 *Run workflow*.

저장소 이름이 경로에 붙는 주소이므로 `--base-href "/<저장소 이름>/"` 가 필요하다.
이걸 빼면 `flutter_bootstrap.js` 를 루트에서 찾다가 404 가 나고 빈 화면만 보인다.
로컬에서 같은 조건으로 확인하려면:

```sh
fvm flutter build web --release --base-href /ddai_lucky_defense/
mkdir -p /tmp/pages && cp -R build/web /tmp/pages/ddai_lucky_defense
(cd /tmp/pages && python3 -m http.server 8098)
# → http://127.0.0.1:8098/ddai_lucky_defense/
```

콜드 로딩은 약 4.7MB다. 자체 호스팅하는 건 `main.dart.js` 뿐이고(2.1MB, gzip 0.6MB),
나머지는 gstatic CDN 에서 온다 — CanvasKit 2.8MB(brotli), Noto Color Emoji 0.69MB,
Noto Sans Symbols2 0.37MB, Noto Sans KR 0.17MB. 두 번째 방문부터는 캐시를 쓴다.

한글 글꼴을 앱에 넣지 않은 이유: 이 게임은 유닛·몬스터가 전부 이모지라 어차피
Noto Color Emoji 가 필요한데, 그건 10MB짜리라 번들이 현실적이지 않다. gstatic 이
막히면 이모지부터 깨지므로, 한글만 번들해도 얻는 게 없다. 대신 Flutter 가 첫
프레임을 그릴 때까지 몇 초가 걸리므로 `web/index.html` 에 HTML/CSS 만으로 즉시 뜨는
로딩 화면을 깔아 두었다.

## 구현 노트

- **카메라 미사용** — 모든 컴포넌트를 `fieldRoot` 아래 화면 좌표 그대로 배치해 좌표 계산이 단순합니다.
  화면 흔들림은 `fieldRoot.position`을 흔들어 처리합니다.
- **`update()` 안에서 `notifyListeners()` 금지** — Flame의 `GameWidget`은 `update()`를
  `LayoutBuilder` 콜백(빌드 단계) 안에서 호출합니다. 그래서 `GameState.notify()`는
  빌드 중이면 프레임 종료 후로 알림을 미룹니다.
- **리사이즈 가드** — `onGameResize`는 위젯이 리빌드될 때마다 호출되므로,
  크기가 실제로 달라졌을 때만 경로·슬롯을 다시 계산합니다.
- **렌더 캐시** — 그라데이션 셰이더, 점선 슬롯 경로, 배경 격자, 이모지 `TextPainter`를
  캐시해 프레임마다 재생성하지 않습니다.
- **배속(×2/×3)** 은 dt를 키우는 대신 서브스텝을 여러 번 돌려 투사체가 적을 건너뛰지 않게 합니다.
- **넓은 화면** 에서는 앱을 480 폭으로 가운데 세웁니다. 세로 화면 기준으로 만든 게임이라
  그대로 늘리면 필드가 납작해지고 버튼만 길어집니다.
- **슬롯 격자는 고정** 입니다(`FieldLayout.slotCols` · `slotRows`). 화면에 맞춰 칸 수를
  늘리면 기기나 브라우저 확대 배율에 따라 놓을 수 있는 유닛 수가 달라져 난이도가
  통째로 바뀝니다. 칸 수는 고정하고 칸 크기만 늘립니다.
- **스크롤은 마우스로도** 끌립니다(`AppScrollBehavior`). Flutter 기본값은 터치·스타일러스만
  드래그로 인정해서, 웹에서는 가로 목록을 마우스로 잡아끌어도 움직이지 않습니다.
- **일시정지** 는 `update()` 를 `super.update(0)` 한 번으로 갈음합니다. 아예 건너뛰면
  대기 중인 컴포넌트 추가·제거가 처리되지 않아, 마침 그 프레임에 죽은 몬스터가 화면에
  남습니다. dt 가 0 이어도 «쿨타임이 0 이하» 조건으로 발사되므로 유닛·투사체에는
  따로 멈춤 검사를 둡니다.
- **자동 판매 대상** 은 `pickAutoSellIndex` 가 고릅니다. 게임 상태가 필요 없는 순수 함수라
  규칙을 그대로 검증할 수 있습니다. 등급이 가장 낮은 것 중에서 «팔아도 합성 횟수가 줄지
  않는 쪽» 을 먼저 고르고, 그래도 여럿이면 보유 수가 적은 것을 팝니다. 유닛이 영구히
  사라지는 동작이라 누르기 전에 무엇이 팔리는지 패널에 미리 표시하고, 팔아도 골드가
  모자라면 아예 팔지 않습니다.
- **최고 기록** 은 `RecordStore` 인터페이스 뒤에 있습니다. 실제 저장은 `PrefsRecordStore`가,
  테스트는 `MemoryRecordStore`가 담당하므로 플러그인 목 없이도 갱신 규칙을 검증할 수 있습니다.
  저장소 I/O는 `onLoad`를 막지 않도록 백그라운드로 돌리고, 읽기/쓰기 실패는 삼켜서
  저장소를 못 쓰는 환경에서도 게임이 그대로 동작합니다.
  게임오버 시점뿐 아니라 앱이 백그라운드로 갈 때도(`AppLifecycleListener`) 기록을 제출해,
  죽지 않고 앱을 닫아도 진행도가 남습니다.
